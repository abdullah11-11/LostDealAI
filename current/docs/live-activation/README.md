Original Sandbox receiver and its environment contract remain intact. All 16 historical migration files remain unchanged. The forward SQL draft changes exactly four existing function predicates and preserves their ACL, owner, SECURITY DEFINER and empty-search_path settings. Those changes recognize Live for atomic import/analysis and prevent future cross-environment rebinding; existing Sandbox lifecycle and simulator ID semantics remain available.

The draft creates an **initially disabled** settings row and **no approved catalog entries or actual authority digest**. Missing adoption, disabled settings, wrong secret, incomplete catalog or revision mismatch produces a safe failure before Live checkout/provider mutation. The Site rejects reuse of its usage/Sandbox authority, and the database rejects a Live key if the current Sandbox verifier would accept it even when a Live digest was mistakenly configured. A browser completion event or supplied subscription status has no entitlement authority.

## Configuration namespaces

The Site runtime and Supabase Edge runtime are separate configuration surfaces. Supabase Edge secrets are project-wide, so flipping an unscoped secret would disrupt the preserved Sandbox receiver. Use the supported environment/secret management interfaces only; never print actual values, commit environment files, use service-role credentials in browsers or give Paddle a Sites bypass token.

| Surface | Configuration after separate approval |
|---|---|
| Existing Sandbox Edge receiver | Retain `PADDLE_ENVIRONMENT=sandbox`, `PADDLE_WEBHOOK_SECRET`, existing billing authority and existing Sandbox contract |
| Separate Live Edge receiver | `PADDLE_LIVE_ENVIRONMENT=live`, `PADDLE_LIVE_STARTER_PRICE_ID`, `PADDLE_LIVE_PRO_PRICE_ID`, `PADDLE_LIVE_STARTER_PRODUCT_ID`, `PADDLE_LIVE_PRO_PRODUCT_ID`, `PADDLE_LIVE_CATALOG_REVISION`, `PADDLE_LIVE_WEBHOOK_SECRET`, distinct `PADDLE_LIVE_BILLING_AUTHORITY_SECRET`, existing supported publishable Supabase URL/key |

Existing usage-runtime authority remains separate. Checkout stays disabled until all acceptance gates pass |

`.env.example` contains blank secret/Live metadata fields and retains safe Sandbox defaults. It is not deployable Live configuration. Real Live IDs must be retrieved and approved; synthetic IDs appear only in isolated tests and must never be used for adoption.

`authority-review-draft.sql` is an **UNAPPLIED REVIEW DRAFT**, deliberately outside `supabase/migrations/`. It is loaded only by the in-memory PostgreSQL test. It is not ledger state and must not be silently applied through db push or bundled provisioning.

2. Review exactly four legacy function predicates against the actual target. The draft requires the exact reviewed `pg_proc.prosrc` SHA-256 from the unmodified source migrations, expected definition pattern exactly once, SECURITY DEFINER and empty search_path; otherwise it raises and the entire transaction rolls back. 4. Apply first to a separately approved isolated persistent environment, with settings disabled and catalog empty. Rerun advisors and verify all private RLS/ACLs and public RPC guards. ## Recovery strategy

The forward review draft is transactional. A failed precondition/advisor/quality gate must abort adoption; do not repair historical functions or ledger entries ad hoc.

Before any Live subscription exists, an approved recovery migration can disable Live settings/destination, prove Live intents/receipts/subscriptions are empty, and restore the exact four captured legacy function definitions with original ACLs/owner/settings. Drop new objects only after these emptiness checks and explicit approval. Retain migration history and the verified pre-adoption snapshot.

After Live records exist, do **not** downgrade to code/functions that do not enforce Live authority. Stop new checkout/provider mutations using approved controls and disable the destination only as part of a reviewed incident plan. Keep saved data readable, preserve provider history and maintain inactive-Live and quota enforcement. Reconcile only through the owner-authorized server read/CAS process after the uncertain-operation cooldown. Repair forward and inspect tenant/function/usage fingerprints; never reset usage, delete history, blindly restore production or let an old event resurrect a canceled subscription. A billing freeze is not a hard AI-provider spending cap: manage provider spending controls separately.

Expected synthetic provider failure logs are safe categorized enums, not private responses. They do not simulate card processing or assert a genuine Paddle overlay.

The current conservative payment-link contract permits automatic USD `ready`, `billed` or `past_due` transactions with one quantity-one approved recurring price, including a zero-value payment-method transaction. Manual invoices, completed/canceled transactions, one-off charges, other currencies and additional items fail closed. Any real-provider behavior outside that contract requires a reviewed narrow change and fresh regressions before approval; do not widen the allowlist merely to pass a genuine payment test. The implementation reads existing `/transactions/{id}` only, never the nominal GET update-payment-method endpoint that can create a provider transaction.

One new test initially expected HTTP503 for a definitive provider rejection; the existing preserved classifier correctly returns HTTP409, while uncertain outcomes return HTTP503. The new expectation was corrected to the established contract. One new component harness initially omitted its required props object; the harness was corrected. No accepted regression assertion, provider failure semantics or application behavior was weakened.
